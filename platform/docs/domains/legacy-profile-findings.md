# Legacy profile: what the data proved

Companion to [`legacy-schema-profile.md`](legacy-schema-profile.md), which
profiles the legacy system from its source code. This file records what two
profiling exports showed when run against a real database — a different kind of
evidence, which in several places contradicts the code reading.

Scripts: [`tools/migration/legacy-profile.sql`](../../tools/migration/legacy-profile.sql)
and [`legacy-profile-2.sql`](../../tools/migration/legacy-profile-2.sql).

## The caveat that governs every number here

**This was a development database, not production.** 190 customers, 23 orders,
17 branches. Findings are marked **structural** — a column that does not exist in
dev does not exist anywhere, a non-nullable foreign key is non-nullable
everywhere, a constraint holds wherever the schema was applied, and an enum
declares its members regardless of which ones appear — or **volumetric**, which
carries over not at all.

Only structural findings may be treated as settled. Every volumetric one is
re-asked against production before its wave runs, and ADR 0024's coverage
register stays blocked until it is.

Two things that look structural and are not:

- **A shared JSON key set is not a shape.** Seventeen rows agreeing on their keys
  is seventeen rows agreeing. The shape is what the *writer* declares — the
  pydantic schema in `apps/dashboard/schemas/`, which is source. Where the writer
  and the rows disagree, the rows are the older population, not the contract.
- **A last-write date is a `MAX()` over rows.** It is better evidence than a row
  count, but it is the same kind of evidence, and a development database goes
  quiet on whatever nobody demos. Its structural counterpart is *whether live
  application code still references the table* — see finding 13.

One dev-specific distortion worth stating plainly: **the order tables were
reseeded.** Orders, line items, payments and transactions all span
2026-02-21 to 2026-04-04 and nothing else, while customers span 2024-02-24 to
2026-07-13. The order history here is a fixture, not a sample.

Source for every structural claim below is `milliy/backend/app` — `models/`,
`shared/enums/`, `apps/*/schemas/`, `apps/*/services/`.

## 1. Three tables no document mentions — structural, and worse than stated

The export discovered 66 business tables. The checked-in models declare exactly
64 (`grep __tablename__ models/` returns 64), and the coverage register claims
all 64 are covered.

| Table | Undocumented |
|---|---|
| `product_import_job_rows` | yes |
| `product_change_histories` | yes |
| `product_import_jobs` | yes |

**Structural, and stronger than "undocumented":** none of the three appears
anywhere in the legacy repository — not as an ORM model, not in any of the 15
alembic migrations, not in the frontend. They are outside the application's own
schema chain. Whatever creates and writes them is not this codebase, so no
amount of reading this repository will produce their disposition.

**Volumetric, and to be re-asked:** the row counts (2 333 / 154 / 6), the
2026-03-07 last-write date, and the read that the jobs table shows *5 completed
and 1 reverted*. The inference drawn from that split — "a bulk catalog import
pipeline *with rollback*, recently used" — rests on six rows in a development
database and is a hypothesis, not a finding. It may well be right; it is not
evidence.

All three still need a disposition before the catalog wave can reach
`CUTOVER_READY`, and getting one means finding the writer, not querying harder.

## 2. Every timestamp is naive, and its zone is the server's — structural

`BaseModel` gives every table `created` and `updated`, typed `DateTime` with no
timezone and defaulted to `datetime.now`. That is Python's *naive local time of
the process*, so the zone of every legacy timestamp is whatever the production
application server is configured to. Nothing in the schema records it, and
nothing in the data can establish it.

This matters more than it sounds: reading them as UTC when they are local shifts
every historical order five hours, across the business-date boundary the daily
order number depends on — a day's orders renumber into the wrong day, and the
reconciliation meant to catch it compares two equally wrong figures.

**Open, and it is a deployment question rather than a data question.** Read the
`TZ` environment variable, `/etc/localtime`, or the container spec of the
production application server. Do not infer it.

For what it is worth and no more: an hour-of-day histogram over this development
database's 372 `otps` rows fits Asia/Tashkent far better than UTC — 2% of
requests overnight and a 35% lunch peak read as local, against 13% overnight and
a 4% lunch read as UTC. That is a plausible-looking hypothesis from a database
whose order tables were demonstrably reseeded, generated by a development server
whose clock need not match production's. It is a reason to expect a particular
answer, not the answer.

## 3. The catalog is branch-owned — structural; the collapse is not measurable

**Structural.** `products.vendor_id` is a non-nullable foreign key to `vendors`
and there is no `company_id`, so a dish belongs to **one branch** while ADR 0016
makes the catalog **brand-owned** with per-location offerings. `legacy-mapping.md`
reads this as a structural re-parenting, and for products and variants it is.

The re-parenting is **asymmetric**, and that part is also structural: neither
`categories` nor `kitchens` carries a `vendor_id` at all. They are already
estate-wide. Only `products` — and `variants` through `product_id` — are
branch-owned. So the wave re-parents one level of the tree, not the tree.

Re-parenting is a supported operation in the legacy application itself:
`apps/dashboard/services/product/product.py` both sets `vendor_id` from input at
creation and reassigns `product.vendor_id` on update. Nothing in the schema
pins a dish to the branch that created it.

**Volumetric, and none of it carries:**

| Brand | Product rows | Distinct names | Branches |
|---|---|---|---|
| `jizbiz` | 650 | 130 | 5 |
| `rayhon` | 665 | 205 | 6 |
| `marmar` | 309 | 257 | 2 |
| `kids_plate` | 1 | 1 | 1 |
| `pharmacy` | 1 | 1 | 1 |

The earlier reading — that 1 626 rows collapse to roughly 594 brand-level
products, a 63% reduction; that `jizbiz` replicates exactly 5× and can have its
collapse defaulted; that `marmar` must not be collapsed at all — is built
entirely on seventeen development branches, three of which hold a single row.
**Withdrawn.** The two branches carrying no products, and the mean of 1.19
variants per dish over 1 917 variant rows, are the same kind of number and are
withdrawn with it. The minimum-viable-cutover assumption that variants are mostly
trivial no longer has evidence behind it.

What survives is the shape of the question, not its answer: name collisions
within a brand each need a decision about whether they are one dish, and the
target must support both outcomes. **What would settle it:** the same
per-brand name/row/branch counts against production, which is also the only way
to learn whether any brand's collapse can be defaulted.

## 4. `kitchens` is a routing category, not a kitchen — structural

`products.kitchen_id` is non-nullable, so `kitchens` cannot be retired and its
`DECIDE` disposition is wrong.

That it is *not a physical kitchen per branch* is now structural rather than
counted: **`Kitchen` has no `vendor_id` and no company scoping of any kind**, and
`apps/dashboard/services/product/kitchen.py` lists every kitchen globally,
ordered by `priority`, with no branch filter available. A kitchen is estate-wide
by construction. It is a preparation-station classification shared across the
estate, which is precisely ADR 0041's production routing. Disposition:
`TRANSFORM`, on schema rather than on a row count.

**Volumetric, and no longer needed:** that only 3 distinct kitchens appear across
1 626 products and 15 branches. It pointed at the right answer; the schema proves
it.

## 5. Opening hours have one uniform shape — structural, from the writer

`vendors.work_time` is a non-nullable JSONB column. Its shape is settled by
`apps/dashboard/schemas/company.py`, not by the rows — see finding 17 for the
full reading:

```
{ working_days: { monday … sunday }, non_working_days: [ {start, end, date} ] }
```

**Structural:** `WorkingDaysSchema` declares all seven weekdays as required, so
any branch written through the dashboard carries a complete week; each day is
`{start, end}`; each non-working entry is a partial-day closure `{start, end,
date}`. This transforms cleanly onto ADR 0036's `service_schedules` +
`service_schedule_rules`, with `non_working_days` becoming schedule exceptions.

**Volumetric:** that the key set is *identical across all 17 branches* and that
there is no long tail. Seventeen rows agreeing is seventeen rows agreeing; the
reason to expect uniformity in production is the required-field schema, not the
count.

**Not solved, contrary to the earlier note.** The open question was framed as
"whether an overnight interval is a wrap or two entries, which needs one branch's
values rather than its keys." Finding 17 answers it from source — the application
has an explicit overnight-wrap branch — and the answer is that wraps are a
single entry whose `start > end`. What remains open is only whether production
*contains* any, which is volumetric.

## 6. Delivery configuration is richer than ADR 0037's model — structural

`vendors.delivery` is a non-nullable JSONB column written by
`VendorDeliveryConfig` in `apps/dashboard/schemas/company.py` and consumed by
`apps/customer/services/cart/calculate_delivery_price.py`. Read from the writer,
the column is a good deal more than a radius and a per-km rate:

- `max_distance` — the hard radius. Enforced in `create_order`, which rejects
  with `DISTANCE_TOO_LONG`. Separately, `vendors.visibility_distance` gates
  whether the branch is offered at all. **Two independent radii.**
- `distance` + `distance_price` — a base band: a distance included in a flat
  base fare.
- `prices_per_km: list[{distance, price}]` — **a stepped tariff, not a linear
  rate.** `calculate_delivery_price` walks the list in order, consuming each
  step's `distance` at that step's `price` until the remaining distance fits.
- `peak_hours: list[{start, end, distance, distance_price, prices_per_km}]` —
  **a full alternative tariff that replaces the base band wholesale** when the
  delivery time falls in the window. It is not a surcharge on the base rate; the
  base `distance`, `distance_price` and `prices_per_km` are all substituted.
- `discount: {value, type: "amount"|"distance", min_order_price?, times?}` — a
  delivery discount carrying **its own time windows**, independent of
  `peak_hours`. `type="amount"` subtracts a sum; `type="distance"` re-runs the
  tariff over a substituted distance, i.e. "the first N metres are free". The
  discount is capped at the computed price.
- Prices and discounts are both rounded to the nearest 500.

**The earlier reading of the two row shapes is wrong.** They were described as
differing by "one optional key", `discount`. In `VendorDeliveryConfig`,
`discount` is a **required field** — no default. So the 15 branches without it
were not written by this schema: they predate it or come from another writer.
That is a fact about the population's history, not about the key being optional.

**Declared but never enforced:** `min_order_price` appears in
`VendorDeliveryConfig` (and inside `discount`) and is read by **no code
anywhere** — not in `calculate_delivery_price`, not in `create_order`. Migrating
it as a live rule would introduce a constraint the legacy system never applied.

**Volumetric:** the 15-versus-2 split across shapes.

**Downstream change.** The earlier conclusion — "exactly ADR 0037's `RADIUS` +
`TARIFF` model … the delivery-zone migration is a field mapping rather than a
redesign" — is too optimistic. ADR 0037 must express *nested per-time-band
tariff tables* and a *distance-denominated discount with its own windows*, or the
mapping is lossy and the migrated prices will diverge from the legacy ones at
peak hours. Confirm ADR 0037 covers both before treating this wave as a field
mapping.

## 7. Order totals reconcile — structural, from the writer, with one correction

There is no `orders.total`; there are `order_price`,
`order_price_without_discount`, `delivery_price`,
`delivery_price_without_discount` and `packaging_price`.

**Structural.** `apps/customer/services/order/create_order.py` is the writer, and
these are its own expressions, not a reconstruction:

```
order_price                     = subtotal − subtotal_discount
order_price_without_discount    = subtotal
delivery_price                  = delivery − delivery_discount   (0 on takeaway)
delivery_price_without_discount = delivery                       (0 on takeaway)
packaging_price                 = packaging
payments.amount                 = (subtotal − subtotal_discount)
                                + (delivery − delivery_discount)
                                + packaging
```

So `total_minor = order_price + delivery_price + packaging_price` is settled by
source, and **equals `payments.amount`** — which gives the migration an
independent check that does not depend on any query. Likewise
`discount = (order_price_without_discount − order_price) + (delivery_price_without_discount − delivery_price)`
is exactly `subtotal_discount + delivery_discount`, computed by two different
functions. Item and delivery discounts must not be summed into one figure,
because ADR 0018 prices them through different stages, and the legacy separates
them for the same reason.

**The line-item reconciliation was wrong.** It was recorded that
`Σ(line.price × line.quantity)` equals `order_price` in every one of 23 orders —
"zero disagreements", "confirmed rather than assumed". That equality is a
property of *that cohort*, and structurally it is false as a rule:

- `calculate_subtotal` **excludes packaging from `subtotal`** and returns it
  separately, while `create_order` appends package lines to `order_line_items`
  with `is_package=True`. So the full Σ over line rows is `subtotal + packaging`.
- Line `price` is the **undiscounted** `variant.price`. `subtotal_discount` is
  never distributed across lines.

The structural identities are therefore:

```
Σ(price × quantity) WHERE NOT is_package  =  order_price_without_discount
Σ(price × quantity) WHERE     is_package  =  packaging_price
```

and Σ equals `order_price` only when `subtotal_discount = 0` **and** no line is a
package — which is exactly the reseeded dev cohort, where 3 products carry a
live discount and no ordered variant had a package. **Downstream change:** any
migration reconstructing a subtotal from line items must filter on `is_package`
and must compare against `order_price_without_discount`, never `order_price`.

**A second line-item trap, structural.** `create_order` copies
`product.discount` and `discount_type or unit` onto **every** line
unconditionally, while `calculate_subtotal` applies a discount only when
`has_discount` is true. A line can carry a nonzero `discount` that was never
charged. Line-level discount fields are not evidence that a discount was applied.

Also structural, from the model:

- `orders.id` is a `BigInteger` autoincrement. The crosswalk is `bigint -> uuid`.
- **`orders.vendor_id` is nullable.** An order with no branch has no brand and no
  tenant, and quarantines rather than being assigned a convenient parent. Dev has
  none; production is the question.
- `orders.planned_time` is written by `create_order` from `cart.delivery_time`
  whenever the cart carries one, and `carts.delivery_time` is validated to be at
  least an hour in the future. Pre-ordering is wired end to end. The structural
  reason to expect it unused is the **writer default**: `Vendor.pre_order`
  defaults to `True` in the ORM but `VendorInputSchema.pre_order` defaults to
  **`False`**, so every branch created through the dashboard has pre-ordering
  off unless someone turned it on.

**Volumetric:** that `planned_time` is set on zero orders; that the cancelled
cohort shows `delivery=155 000` against `delivery_no_disc=170 000`; and the
23-order line reconciliation itself.

## 8. Five sales channels are declared, three appear — structural

**Structural.** `orders.platform` is a non-nullable `enums.Platform`, and that
enum declares **five** members: `android`, `ios`, `web`, `telegram`, `support`.
That is ADR 0036's sales channel registry under another name, and the registry
has five entries whatever a given database happens to contain.

`create_order` writes `platform = session.device.platform` — the customer's own
device platform, whose column default is `android`. So `android`/`ios`/`web`
originate in the customer app, and `telegram`/`support` necessarily come from
other writers. Telegram being a real ordering surface rather than a notification
one is corroborated structurally: `vendors` carries both `tg_chat_id` and
`tg_delivery_chat_id`.

**Structural, on operators.** `orders.operator_id` is a nullable FK to
`dashboard_users` and is **completely independent of `platform`** — no constraint
ties them, and `create_order` never sets it. The model therefore permits an
operator on an order from any channel, which means ADR 0039's amendment path maps
onto an existing capability rather than a new one. `dashboard_users.role` is
`admin`/`manager`/`dispatcher`.

**Structural, on order types.** `create_order` writes `type_id` of only
`takeaway` or `delivery`, chosen from the requested delivery method. The customer
checkout has **no path** that produces `on_time`, `express` or `external`; those
must come from another writer or are vestigial. They stay a quarantine reason.

**Volumetric, and to be re-asked:** the `web` 14 / `telegram` 8 / `support` 1
split; that `operator_id` is set on 8 of 23 orders against 1 `platform=support`
order, and the "a third of orders are operator-made" headline built on it; and
that all 23 orders are `type=delivery`. **What would settle the operator
question:** the same `platform × operator_id` cross-tab against production, which
also sizes the amendment history to migrate.

## 9. Merchant accounts are per-branch-per-method — structural, by constraint

**Structural.** `fin_agents` carries
`UniqueConstraint("payment_method_id", "vendor_id", name="unique_pm_vendor")`.
Merchant accounts are therefore per-branch-per-payment-method **by constraint** —
at most one agent per (branch, method) pair, and the topology cannot be
per-platform or per-brand without violating it.

`create_order`'s `validate_payment_method` looks the agent up by exactly that
pair and rejects with `METHOD_NOT_AVAILABLE` when it is missing, so a branch
without an agent for a method cannot accept that method. The branch, not the
platform, is the settlement counterparty.

This closes ADR 0013's open input on merchant topology, and it corroborates the
decision that **the restaurant is the principal**: each branch settles through
its own agents, one per method it accepts.

**Volumetric:** that there are 24 rows for 17 branches, and that 4 are referenced
by transactions in this database.

## 10. Customer identity must be `BRAND_ISOLATED` — structural, by constraint

**Structural, and it does not rest on four rows.** `customers` carries
`UniqueConstraint("username", "company", name="uq_customers_username_company")`,
and every authentication entry point is keyed on that pair:
`get_or_create_customer` in `apps/customer/services/authentication/login.py`
selects on `username == phone AND company == company`, `verify_otp` does the
same, and the dashboard's customer service filters by `company` throughout.

It follows that a phone registering under `rayhon` and under `jizbiz`
**necessarily** produces two rows with distinct ids — and therefore distinct
carts, distinct orders, distinct addresses. This is true of any database this
application wrote, whether the overlap is four phones or forty thousand.

**The tenant's identity mode is `BRAND_ISOLATED`**, and the reasoning is now a
constraint rather than a count: with every company becoming a brand under one
HorecaOS tenant, sharing accounts across brands would merge people the legacy
system kept apart by design, and ADR 0015 and ADR 0024 both forbid merging people
on a matching phone. The four dev phones spanning two partitions are an
illustration of the constraint, not the evidence for it.

**The archive mechanism was read backwards.** It was recorded that "the legacy
archives a customer by writing a new row and pointing `archive_id` at the old
one", and concluded that "half the customer table is superseded history" to be
imported as history behind the head of each chain. Source says otherwise:

- `get_or_create_archive_customer` creates a **twin at signup**, in the same
  transaction as the real customer, with `username = "archive_" + phone`, the
  same `company` and `phone`, and `extra = {}`. The twin's own `archive_id` is
  null.
- The live customer is then created with `archive_id` pointing at that twin, and
  it never changes.
- The twin is a **soft-delete holding pen**, not a prior version:
  `apps/customer/services/address/delete.py` sets
  `address.customer_id = customer.archive_id`, and `device/delete.py` does the
  same for devices, re-keying them under the twin.

So `customers` holds exactly **two rows per person per brand** — one live, one
tombstone — and there is no chain. The three counts that were read as a
coincidence are one fact seen three ways: 95 people × 2 rows gives 95 rows with
an `archive_id`, 95 rows with empty `extra`, and 95 "duplicate phones within one
partition". The duplicate phones are the live/tombstone pair, which is precisely
why `UNIQUE(username, company)` is not violated — the usernames differ by the
`archive_` prefix.

**Downstream change, structural.** The migration rule is not "import the head of
each chain and the rest as history". The application's own definition of a real
customer is `archive_id IS NOT NULL` — `apps/dashboard/services/customer.py`
filters exactly `~Customer.archive_id.is_(None)` to list customers. Import those
rows as accounts. The `archive_*` rows are **not people**; they are parents for
orphaned addresses and devices and must be reconciled — those child rows either
migrate as detached history or are dropped — not imported as customer history.

**A caution on the brand crosswalk, structural.** `customers.company` is a plain
`str` column, not a foreign key and not a database enum, with column default and
server default `rayhon`. `verify_otp` also defaults its `company` argument to
`rayhon`. And `companies.slug` carries **no unique constraint**. So the crosswalk
is string equality against an unconstrained column, and `rayhon` rows may include
rows where the brand was simply never supplied. What is structural is that the
writer is restricted to the five members of `enums.Company` — `rayhon`,
`marmar`, `jizbiz`, `kids_plate`, `pharmacy`. That every value happens to match a
`companies.slug` is a data observation and is **volumetric**; verify it in
production before relying on a slug-based crosswalk, and expect `rayhon` to be
over-represented by defaulting.

**Structural, on `extra`:** the column is non-nullable, and the only keys any
code writes are `has_profile_data` and `has_address` at creation, `otp_tries`
via `set_otp_tries`, and `otp_limit` read during login throttling
(`has_address_data` appears in the data but has no writer in this codebase).
Onboarding flags and a rate-limit counter, no business data. It does not migrate.

## 11. Storefront content is a three-table structure — structural

**Structural.** `enums.UiElementType` declares **four** types — `category`,
`banner`, `offer`, `popular` — not two. `apps/customer/services/ui/elements.py`
queries three of them with a dedicated query each (`get_categories`,
`get_offers`, `get_populars`); **`banner` has no reader anywhere** in the
customer app.

Storefront content is three tables, not one:

```
ui_elements ──< ui_element_items ──> categories | products | ui_offers
```

`ui_element_items.type` is `product`|`category`|`ui_offer` with a matching
nullable FK for each, and `ui_offers` carries `order_button_text`,
`order_button_action` from a four-value enum (`open_items`, `open_category`,
`open_cart`, `open_url`), and optional `product_id`/`category_id` targets. So the
capability is a merchandising surface with typed call-to-action targets, not a
flat promotional block — richer than described, and **specifiable**, which was
the conclusion and still is. It is not the unclassifiable JSON the coverage
register feared.

Every element is `vendor_id`-scoped and non-nullable, so merchandising is
branch-scoped. All three queries select the element by joining to the customer's
**cart vendor**, not by distance — and `ui_elements.visibility_distance`, though
non-nullable with default 0, is **read by no query in the codebase**. Declared
and unused, like `min_order_price` in finding 6.

**Volumetric:** that only `offer` (14) and `popular` (2) appear, and that the
last write was 2026-02-14. Whether `category` elements and the reader-less
`banner` type exist in production is unknown, and `category` elements have a live
reader that would break differently if absent.

## 12. Branch location cannot be trusted, and the schema cannot help — structural

**Structural.** On `vendors`, `latitude`, `longitude`, `address` and `city_id`
are all **non-nullable**, so V0023's new columns on `tenant.locations` can be
filled for those four from any row. `phone` and `tin` are **nullable in the
model** but **required by `VendorInputSchema`** — so every branch created through
the dashboard has them, while the column itself permits null and another writer
need not supply them. Treat their completeness as likely, not guaranteed.

**Structural, and the real point:** `latitude` and `longitude` carry **no CHECK
constraint and no validator**. Contrast `Vendor.rating`, which has an explicit
`@validates` asserting `0 <= rating <= 5`. The schema is capable of rejecting bad
coordinates and does not. Nothing prevents (0, 0) — a real point in the Gulf of
Guinea that every distance calculation and every ADR 0037 zone test will accept —
or any other plausible-looking wrong point. **Screening for it in production is
mandatory regardless of what dev contained**, because the schema offers no
guarantee to lean on.

**Volumetric:** that all 17 branches have no nulls and no half-pairs; that
exactly three sit at (0, 0); that 14 of 17 are genuinely locatable. The three
quarantine in this database. The production count is a different number.

## 13. Dispositions: last-write dates are volumetric, code references are not

The first pass offered only row counts. The second added last-write dates and
called them "far better evidence: a table with rows that stopped being written
two years ago is a feature that has already been retired by everyone except the
schema." **That over-reads them.** A last-write date is a `MAX()` over rows in a
development database, and a development database goes quiet on whatever nobody
demos. It is the same class of evidence as a row count, and the governing caveat
applies to it in full.

The structural counterpart is whether **live application code still references
the table**. That is a property of the source, holds in production, and it cuts
across the date evidence rather than agreeing with it.

**Structurally orphaned — no reader and no writer anywhere in the application:**

| Source | Note |
|---|---|
| `configs` | `enums.Config` declares keys; **nothing queries the table.** Equivalents come from `settings` (env). |
| `tax_receipts` | `create_invoice` writes `transactions` and calls the Click SDK, and never touches this table. |
| `offers`, `offer_orders`, `offer_users`, `offer_users_used` | See finding 14 — readable via `cart.offer`, but unreachable. |
| `stocks`, `tags`, `product_tags`, `recommended_products` | No code at all. |
| `incidents`, `action_logs`, `logs` | No code at all. |

These are `RETIRE` or `ARCHIVE` on structural grounds, and the case does not
depend on a production re-query.

**Live code paths despite dead dev data — their silence proves nothing:**

| Source | Last written in dev | Live code |
|---|---|---|
| `search_histories` | 2024-05-18 | yes — 4 references |
| `notifications` | 2024-06-20 | yes — 6 references |
| `notification_preferences` | 2024-04-29 | yes — 7 references |
| `couriers`, `courier_groups`, `courier_group_*`, `areas`, `courier_locations` | 2024-08-10 / 2025-07-14 | yes — an entire FastAPI sub-application (`apps/courier/`) with its own routers, authentication and `courier_otps`, plus dashboard services; 50+ references |
| `vendor_users` | 2024-03-04 | yes — 21 references |
| `customer_invitations` | 2024-03-17 | yes — 6 references |
| `ratings` | never | yes — 6 references |
| `black_lists` | never | yes — enforced at login |
| `faqs`, `faq_categories` | Feb 2024 seed | yes — read by `services/support/faq.py` |
| `social_medias` | Feb 2024 seed | yes — read by `services/support/social_media.py` |

**Two dispositions are reversed.** `search_histories` and `customer_invitations`
were moved to `RETIRE` "on two-year-dead evidence"; both have live routes, and
the evidence was a dev `MAX()`. They return to candidate, pending production.
Calling the **entire courier subsystem** retired on a dev last-write date is the
same error at much larger scale — that is a whole running application.

**Two expectations are reversed.** It was recorded that for `configs` and
`tax_receipts` "the opposite is near-certain in production." No code reads or
writes either one. `create_invoice` implements Click, leaves Payme an
unimplemented `pass`, and asserts that anything else is cash — no receipt is ever
produced. Expect both tables to be as empty in production as in dev, and treat
the "`configs` key inventory" open question as probably a non-question.

**The fiscal data that does exist is on `variants`, and it is structural.**
`variants.spic_id`, `variants.unit_code` and `variants.vat` are all
**non-nullable**. Every variant carries a product classification code and a VAT
rate even though no fiscal receipt is ever written. That, not `tax_receipts`, is
ADR 0038's input, and it is available for every row.

**Three dispositions strengthen.** `tags`, `product_tags` and
`recommended_products` were candidate `RETIRE` on emptiness alone; with no
referencing code anywhere they are `RETIRE` structurally.

**Seed data, written once in Feb 2024 and never since**: `cities`, `statuses`,
`order_statuses`, `order_types`, `delivery_methods`, `payment_methods`, `faqs`,
`faq_categories`, `social_medias`. Reference tables, not features — all of them
still read by live code, so none is a retirement candidate on its date alone. And
note finding 15: their *content* in dev is a partial and partly wrong seed, while
their *domains* are declared in enums and are structural.

**Alive**: `products`/`variants` (to 2026-02), `ui_element*` (2026-02),
`favourite_products` (2026-02), `customers`/`addresses`/`devices`/`sessions`
(2026-07), `carts` (2026-07), `product_import_*` (2026-03). All volumetric.

## 14. Promotions are trivial — structural, for a different reason

**Structural, on product discounts.** `calculate_subtotal` applies a discount
**only when `products.has_discount` is true**, and only then reads `discount` and
`discount_type`. `discount_type` is a nullable column that is never consulted
otherwise. So the trap is structural rather than a property of 523 rows:
`discount_type` is not a flag and never was, and any migration keying off the
type column instead of `has_discount` will import discounts the legacy system
never applied. Finding 7 records the line-item version of the same trap.

**Structural, and a genuine source inconsistency.** `enums.DiscountType`
documents `flat  # 1000` and `unit  # 10%`. `calculate_subtotal` follows that —
`unit` is a percentage, `flat` an absolute sum. `get_offer_discounts`
**inverts it** for `order_price` scope, treating `flat` as a percentage and
`unit` as an absolute. The two writers disagree, so `discount_type` semantics are
writer-dependent and cannot be interpreted uniformly across `products`,
`order_line_items` and `offers`.

**Structural, on the offers engine.** `offers` is a complete promo-code model —
vendor-scoped, `promo_code` unique, `type` `promo_code`|`discount`, `scope`
`order_price`|`delivery_price`|`total_price`, `audience`, usage caps
(`total_count`, `per_user`, `track_*`), a validity window with an `eternal`
override, and a `from_sum` threshold — and `get_offer_discounts` reads it on the
checkout path via `cart.offer`. But **nothing in the codebase creates an `Offer`
and nothing sets `carts.offer_id`**: there is no offers router and no assignment
anywhere. The engine is structurally unreachable, so `get_offer_discounts` can
never fire.

That makes the conclusion — the promotion migration is trivial rather than a
blocker — correct, but for a structural reason rather than because three rows
happened to be live. It also means the empty `offer_*` tables in finding 13 are
orphaned by construction, not merely undemoed.

**Structural, on inventory.** `products.stock_enabled` is a non-nullable bool
defaulting to false, and `Variant.validate_availability`'s stock check reads
`not (stock_count > 0) and stock_count > quantity` — a condition that cannot hold
for any non-negative count, so it never raises. (`create_order` has a separate,
working check.) Inventory is unused *and* the model-level guard is broken. The
minimum-viable-cutover decision to ship `BINARY` or `UNTRACKED` only stands.

**Volumetric:** that `discount_type` is set on 523 products (`flat` 515,
`unit` 8) while `has_discount` and `time_enabled` are true on 3 each, and that
`stock_enabled` is 0 across all 1 626 products. The stale-`discount_type`
population in production is a different number; the trap is the same.

## 15. Reference data: the enums are the domain, the seed is partial and wrong

Every one of these tables has an `id` column typed as a Python enum. **The enum
is the domain and is structural; the seeded rows are a population and are
volumetric.** All four sub-findings were previously read off the rows.

**`cities` — the key is authoritative, the label is wrong data.** `cities.id` is
an enum over **14 values**, one per Uzbek province, and the model's own docstring
cites `ISO 3166-2:UZ`. `enums.City` maps `andijon → uz-an`, `toshkent → uz-to`,
`toshkent_shahri → uz-tk`, and so on. The `name` column is free JSONB carrying
only a language-presence validator — nothing checks it against the key.

**Downstream change.** It was recorded that a row keyed `andijon` labelled
"Tashkent city" / "Город Ташкент" "cannot be mapped by a rule; it needs a
decision per row". It can: **map by key to ISO 3166-2:UZ and discard the label.**
The key is a standardised code the application itself declares; the label is
unvalidated seed text. This is a mislabelled row, not an ambiguity, and it needs
data repair rather than a per-row migration decision. The observation that it
"silently mislabels every address that references it" stands and is worth
reporting to whoever still runs the system.

*Volumetric:* that only 3 of the 14 provinces are seeded, and which labels are
wrong. Production may seed more, and may mislabel different ones.

**`order_statuses` — the mapping is settled; both stated gaps are wrong.**
`enums.OrderStatus` is exactly `new`, `accepted`, `cooking`, `ready`,
`delivering`, `completed`, `cancelled`, each with a target counterpart. That much
was right, and is structural.

But it was recorded that "what the legacy lacks is any distinction between
rejected, expired and cancelled, and any payment state at all". Both are false:

- **Cancellation reason exists.** `orders` carries `cancel_reason` (text),
  `cancelled_by_id`, and `cancelled_by_type` — an enum of
  `customer`|`vendor`|`dashboard`. That is the source for resolving a cancelled
  legacy order into the target's three terminal reasons; it needs a mapping
  decision, not another source.
- **Payment state exists, in four places.** `orders.payment_status` is a
  non-nullable `PaymentStatus` (`new`, `in_progress`, `completed`, `failed`,
  `cancelled`) with server default `new`; `orders.payment_method` and
  `orders.payment_transaction_id` sit beside it; `payments.status` and
  `transactions.status` carry the same enum independently. There is also
  `cooking_status` (`CookingStatus`) and `shipment_status` (`ShipmentStatus`),
  both non-nullable — the legacy tracks three parallel lifecycles, not one.

**Downstream change:** a cancelled legacy order *can* be resolved into a terminal
reason from `cancelled_by_type` + `cancel_reason`, and order payment state does
not need to be reconstructed from the payments tables. Both were listed as
blockers and neither is.

**`order_types` — five members, not four.** `enums.OrderType` is `delivery`,
`express`, `external`, `takeaway`, `on_time`. `external` was omitted entirely
from the earlier reading. The conflation point stands and is structural: the
target's `FulfillmentMode` is `DELIVERY`/`PICKUP`/`DINE_IN`, so `on_time`
(scheduling) and `express` (service level) are not modes and the row does not say
which mode they carry. `external` is a third axis again — provenance — and needs
its own decision. Per finding 8, the customer checkout writes only `delivery` and
`takeaway`.

**`payment_methods` — seven members, not three.** `enums.PaymentMethod` declares
`cash`, `click`, `payme`, `online`, `terminal`, `free`, `bank_transfer`. The
earlier statement that "`payment_methods` is `cash`, `click`, `payme` — the two
providers ADR 0013 needs" was a count of a seed table in a development database.

Structurally, three of the seven are implemented: `create_invoice` handles
`click` via the Click SDK, leaves `payme` an unimplemented `pass`, and asserts
that anything else is `cash` — **and that assertion means an order paid by
`terminal`, `free` or `bank_transfer` raises at invoice creation.** So the other
four are declared-only in this code path.

**Downstream:** ADR 0013 must confirm which methods the *production* seed
contains before treating Click and Payme as the complete provider set. A
production `payment_methods` row for `terminal` or `bank_transfer` — plausible
for a restaurant estate — means fin-agent rows, historical payments, and a
settlement path that ADR 0013 currently has no home for. **What would settle it:**
`SELECT id FROM payment_methods` and the distinct `payment_method_id` on
`fin_agents` in production.

## 16. `vendors.managers` is empty — and that is structural after all

All 17 branches in this development database carry JSON `null`, not an empty
array. That count is volumetric. **But the writer settles it:**
`apps/dashboard/services/company/vendor.py` creates every vendor with
`managers=None` hardcoded, and **no code path anywhere assigns the column** — the
only other reference in the application is the serializer that reads it back out.
The column is dead in any database this application wrote.

So the earlier demotion was too cautious in one direction: the branch-to-staff
link that `legacy-mapping.md` treats as the input to the Keycloak crosswalk does
not exist as data, and the identity-link process starts from a blank sheet. That
is now settled rather than pending a production re-ask. (The column is also
declared `Optional[list[dict[str, str]]]` while wrapped in `MutableDict` — a
type error that would misbehave if anything ever did write it.)

What was already structural stands: ADR 0024 forbids treating either `managers`
or `vendor_users` as authoritative identity regardless of how full they are —
every operator resolves to a Keycloak subject through an approved link process —
so the migration's behaviour does not change with the answer. Only the amount of
manual work does, and it is now known to be all of it.

## 17. Opening hours: the shape is structural, the contents are not

Read from `apps/dashboard/schemas/company.py`, which is what writes the column,
rather than from the rows:

- `WorkTimeSchema` is `{start: time, end: time}`. **The keys are `start` and
  `end`** — neither the `from`/`to` nor the `open`/`close` that two drafts of the
  profiling script guessed at. Structural.
- `WorkingDaysSchema` declares all seven weekdays as **required** fields, so any
  branch written through the dashboard carries a complete week. Structural.
- `NonWorkingDaysSchema` extends `WorkTimeSchema` with a `date`, so a closure
  exception is `{start, end, date}` — a partial-day closure, not merely a
  calendar entry. Structural, and it answers what is inside the
  `non_working_days` entries without another query.
- The schema's **defaults are `10:00:00` and `23:00:00`**, serialised by pydantic
  as `HH:MM:SS`. So the `HH:MM:SS` format is not one odd branch; it is what the
  dashboard writer produces by default. `HH:MM` comes from elsewhere — seeds, or
  an older writer.

That last point makes an earlier finding worse rather than milder. The schema
profile found that `get_pre_order_time_slots` crashes on `HH:MM:SS` while
`Vendor.active` accepts both. Combined with the defaults above, **the dashboard's
own default opening hours break the legacy pre-order slot code**. Any branch
saved through the dashboard without hours being edited is in the failing format.
Structural, and worth reporting to whoever still runs this system.

**Overnight wrap is supported and must be handled.** `Vendor.active` contains an
explicit branch for it:

```python
# Overnight shift: e.g. 09:00 to 05:00 (next day)
return current >= start or current <= end
```

`calculate_delivery_price._time_in_range` carries the identical branch for peak
hours and delivery-discount windows, and `Variant.validate_availability` carries
it again for product availability windows. Wrapping intervals are a first-class
concept across the application, not a quirk of one function.

`get_pre_order_time_slots` is the exception, and it fails twice over: it parses
with `"%H:%M"` (crashing on the writer's own default format) and then
`continue`s whenever `start > finish` — so a branch with genuinely overnight
hours silently offers **no pre-order slots at all** rather than erroring. Both
behaviours are structural.

An earlier revision of this document claimed no branch wraps past midnight and
called it settled. That was read off seventeen development rows and is
withdrawn: the application anticipates wrapping hours in four places, so
production may well contain them, and ADR 0036's schedule rules have to support
the wrap its preparation bands deliberately do not.

**Volumetric, and not to be relied on:** that 11 of 17 branches sit at
`00:00–23:59`, that 5 sit at `09:00–22:00`, and that exactly one uses
`HH:MM:SS`. The `00:00–23:59` sentinel is worth *looking* for in production —
migrating it literally produces a window that closes for one minute a day rather
than an all-day rule — but its prevalence here says nothing about its prevalence
there.
