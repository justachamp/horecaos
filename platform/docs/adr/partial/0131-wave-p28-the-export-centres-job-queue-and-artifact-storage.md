## Context

Row `7.2e` and ADR 0043's own text agree that an export ships last,
"deliberately, behind capabilities and an audited job queue" — and ADR
0029's egress checklist names the missing control by the same words a prior
audit used: "no data-subject export ... operation exists anywhere". Neither
existed before this wave: `Capability` registered only `REPORTING_READ`, no
`reporting.report_exports` table existed, and the console's own Export
button was hard-coded `disabled`.

Three shapes were not settled by the brief and had to be decided here:

1. **Where does the artefact live?** The platform already has one binary
   storage lifecycle — `media.assets` (ADR 0010) — with its own
   `MediaAssetService`, a `PENDING_UPLOAD → UPLOADED → AVAILABLE` state
   machine, and an image-only verification pipeline (`ALLOWED_IMAGE_TYPES`,
   `widthPx`/`heightPx` required on `markAvailable`). A CSV export is not an
   image and has no client to presign an upload for; it is generated by the
   platform itself, the same shape `MediaDerivativeWorker` already writes
   through `ObjectStorage#put` without a `media.assets` row at all.
2. **How wide is the capability grant?** `report.export` and
   `customer.pii.export` are new, and nothing in the brief said which
   bundles should hold either.
3. **How many reports does the export centre answer for on day one?** The
   row names "Excel/CSV export... plus the export centre" generally; only
   the customers module's own `CustomerListQueryService#exportFiltered`
   shape was named as the thing to model the job on.

## Decision

**Artefact storage.** `reporting.report_exports` stores the artefact's
`bucket`/`object_key`/`content_type`/`size_bytes`/`checksum_sha256`
directly on the job row and writes bytes through the media module's own
`ObjectStorage` port (`media.api`, ADR 0010) via `ObjectStorage#put` — the
same "platform produced this object itself" path `MediaDerivativeWorker`
already uses, at key `tenants/{tenantId}/report-exports/{exportId}.csv`,
under the same configured bucket the media module uses by default
(`horecaos.reporting.exports.bucket`, falling back to
`horecaos.media.bucket`). No row is written to `media.assets`: that table's
lifecycle exists to answer "is this safe to show a customer", a question a
staff-only, capability-gated CSV never asks. `GET
.../reporting/reports/{id}` presigns a five-minute download URL the same
way `MediaAssetService#downloadUrl` does for a private asset.

**Capabilities.** `report.export` (TENANT) is held by `TENANT_OWNER`,
`TENANT_ADMIN`, and `TENANT_FINANCE` — the three bundles already holding
`REPORTING_READ` at the widest, tenant-wide scope, on the reasoning that
taking a figure out of the console is the natural next act of whoever can
already see the whole of it. `customer.pii.export` (TENANT) is held by
`TENANT_OWNER` alone, mirroring `AUDIENCE_EXPORT`'s own placement and
argument exactly: a bulk export over however many customers a filter
selects is the same blast radius as an audience download, and ADR 0029's
own checklist names bulk PII egress as the risk this capability exists to
gate.

**Scope for this wave.** Only `ReportExportRegistry.CUSTOMER_DIRECTORY` is
wired, reusing `CustomerListQueryService#exportFiltered` (PII path) and
`#list` (non-PII path) through a new inverted-dependency port,
`customers.api.CustomerDirectoryExportPort`, exactly the shape
`CustomerOrderActivityPort` already establishes in the opposite direction.
`ReportExportService#run` is a single `if` on `reportKey` rather than a
pluggable `ReportExportSource` interface — a registry of one report has
nothing for an abstraction to select between yet (AGENTS.md: "Do not
introduce infrastructure or patterns only for hypothetical scale").

**Row quota.** A PII-included export is bound by
`CustomerDirectoryExportPort.PII_ROW_LIMIT` (2000 — the pre-existing
`CustomerListQueryService.EXPORT_LIMIT`, now referenced rather than
duplicated). A non-PII export is bound by `ReportExportService
.DEFAULT_ROW_QUOTA` (5000), a new, platform-fixed ceiling — not yet a
tenant setting.

## Alternatives considered

| Option | Why not chosen | Revisit when |
|---|---|---|
| Store the CSV as a `media.assets` row through `MediaAssetService`'s ordinary upload lifecycle | That pipeline decrypts nothing but decodes and probes *images*: `ALLOWED_IMAGE_TYPES`, `widthPx`/`heightPx` `NOT NULL` on `markAvailable`, and `MediaVerificationWorker`'s whole job is "is this really a photo". Forcing a CSV through it means either widening the image allow-list (a real security-relevant surface for an unrelated feature) or hand-writing fake width/height, neither of which the pipeline's own reviewers would expect to see change for an export feature. | A second binary export format needs thumbnailing, format conversion, or customer-facing visibility — none of which a staff-only audit artefact needs. |
| A dedicated `reporting-exports` S3 bucket from day one | No infra exists yet to provision it, and the media bucket's own private-with-signed-URL posture already satisfies ADR 0010's requirements for this artefact; a second bucket is one config value away (`horecaos.reporting.exports.bucket`) whenever ops wants the isolation. | An audit finds a reason the two artefact classes must not share physical storage (differing retention windows, differing access logs). |
| A generic `ReportExportSource` plugin interface, selected by `reportKey` | One implementation (`CustomerDirectoryExportPort`/`CustomerDirectoryExportAdapter`) cannot prove an abstraction is right; the first real second report (an order-log or a payment-mix export) will show what actually varies — pagination shape, whether a source needs its own row quota, whether every source can share one CSV writer. | A second report joins the registry — write the interface then, against two real call sites instead of one imagined one. |
| `report.export` held more broadly (e.g. also `BRAND_MANAGER`, who already holds `REPORTING_READ`) | `BRAND_MANAGER` is brand-scoped; this capability is declared `TENANT` only (the brief's own text), and a bulk egress control is more defensible starting narrow than starting wide — the same reasoning that kept `AUDIENCE_EXPORT` off every bundle but the owner. | A tenant reports that brand managers routinely need this and are blocked waiting on the owner; widening a capability's bundle list is a one-line change with no migration. |
| A real `.xlsx` binary via Apache POI | No POI dependency exists on this build, `commons-csv` already does (used by the customer CSV import); "Excel/CSV" in the row's own title reads as "a file Excel opens", which a CSV already is. Adding a new heavyweight dependency for formatting alone is exactly the kind of infrastructure-for-hypothetical-polish AGENTS.md warns against. | A tenant asks for multi-sheet workbooks, cell formatting, or a size an operator's spreadsheet tool mishandles as CSV. |

## Consequences

### Positive

- ADR 0029's checklist item is no longer unmet: every bulk export of
  customer data is now capability-gated, queued, and recorded with who
  exported what, how many rows, and whether the PII group was included.
- The artefact lifecycle reuses proven, tested infrastructure
  (`ObjectStorage`, its S3 adapter) rather than inventing a second object
  store client.
- `CustomerListQueryService.EXPORT_LIMIT`'s silent-truncation gap (the
  row's own named trap) is closed as a side effect of building this: the
  constant is now public, referenced rather than duplicated, and covered by
  a test that actually exceeds it.

### Negative

- Only one report is exportable today. An operator opening
  `/statistics/exports` from any report page other than a customer list
  sees a screen that can only ever produce a customer directory, which
  reads as a smaller win than the row's own "Excel/CSV export... of any
  report" framing implies.
- The row quota (5000 for a non-PII export) is a code constant, not a
  tenant-configurable value — a tenant with a genuinely larger customer base
  than that will see `truncated: true` with no self-service way to raise it.
- The artefact shares the media bucket by default. A retention or
  access-logging policy written for media images (thumbnails, public CDN
  origin) does not automatically fit a private, staff-only CSV, and nothing
  enforces that the two stay distinguishable beyond the key prefix
  (`report-exports/` vs. an asset's owner-scoped path).
- No sweep ever deletes a settled export's artefact. `media.assets` has an
  explicit `DELETION_REQUESTED`/`DELETED` lifecycle this table does not
  reuse; an export left `COMPLETE` keeps its object indefinitely.

### Accepted trade-offs

Building the general job queue, both capabilities, and the screen while
wiring only one report is the trade-off row `7.2e`'s own two-day estimate
forced: a second report is real, incremental work (a registry entry plus a
data-fetching branch), not a redesign, so shipping the mechanism narrow now
and widening it later costs less than either blocking this wave on every
report or guessing a plugin shape no second call site has tested yet.

## Rollout and rollback

`ReportExportWorker` is gated by
`horecaos.reporting.exports.scheduler.enabled` (default true), the same
switch shape every other durable worker on this platform uses — setting it
`false` stops processing while leaving `QUEUED` rows as evidence of demand,
with no artefact ever produced from them. Rolling back the whole wave is a
schema no-op: nothing outside `reporting.report_exports` and the two new
capabilities references any of it, so reverting the code leaves an inert
table and two ungranted capabilities.

## Exit criteria

An operator holding `report.export` can queue and download a customer
directory export from `/statistics/exports`; one holding it without
`customer.pii.export` gets a file with the phone column absent rather than
a refusal; and `audit.audit_events` carries one `report.export.completed`
fact per completed job naming the report, the row count, the PII group, and
the (non-PII) filters used — all four proven by
`ReportExportServiceTests`.
